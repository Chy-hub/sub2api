# 个人功能分支审查（2026-10-02）

审查基线：`458b92abd`（本地 `upstream/main`，0.2.12）；个人分支起始提交：`ac60cf701`。范围是两者之间的 12 个提交、114 个文件，而非落后于实际分叉点的本地 `main`。本报告与本次工作区修复一起交付。

审查尺度：本分支以满足个人特殊需求为目标，优先简洁有效、容易维护。明确影响日常使用的错误和无用代码直接处理；低频操作、尚未出现在实际配置中的组合，以及更严格的并发一致性要求，可以作为已知限制保留。下列边界与可选优化不作为上线前必须整改的清单。

| --- | --- | --- |

## 已修复的问题

1. **P2：WebSocket 资格过滤在账号池补充后失效。** 原入口先排除关闭 WS 的账号，但协调器下一轮补充池成员时重新加入它们，可能选中禁用账号而忽略仍可用的账号。将 transport 要求随等待任务传递，在候选过滤、数据库复核和完整账号装载后检查；覆盖默认与实验调度入口。
2. **P2：额度刷新未就绪时可能空指针。** 候选额度检查可以返回 `nil`；未启用调度快照的路径在检查隐私设置之前未判断空值。现提前拒绝候选，避免请求 panic。
3. **P2：等待许可的 Redis 重试不幂等。** 当首次执行已取得最后一张许可但响应丢失时，重试会先发现队列满额并返回拒绝。现优先确认同一 token 的现存许可，既不重复占位，也不延长原到期时间。
4. **P2：分组查询失败被汇总为零容量。** 顺序查询回退路径虽跳过失败账号查询，仍把失败的分组 ID 交给汇总器。现只汇总成功查询的分组，继续保留真实空分组。
5. **P2：额度探测响应串到其他账号行。** 前端组件切换账号后，旧异步请求仍可覆盖新行的数据。现用发起时账号 ID 和请求序号校验，丢弃迟到响应，并补充回归测试。
6. **P2（内存侧已修复）：更换凭证后复用旧探测任务和缓存。** 原 singleflight 与刷新缓存仅以账号 ID 区分。现加入端点、API Key 和实际自定义请求头的摘要，并防止旧任务覆盖其他身份的内存结果。持久化快照的边界仍未解决，见下节。
7. **P2：额度探测基址包含查询串等附加部分。** 直接拼接 `/key/info`、`/user/info` 会把路径拼入 query/fragment；现拒绝包含 userinfo、query 或 fragment 的探测基址。
8. **P2：不完整响应可能被解析为成功额度。** 原代码忽略 body 读取错误并静默截断到 256 KiB；`gjson` 仍可能从无效 JSON 中读到部分预算字段。现检测读取错误和超限，并验证完整 JSON；无效 `/key/info` 响应不写回快照，无效 `/user/info` 响应不补充预算窗口。新增截断、拼接多个 JSON 和超限响应回归用例。

## 当前约定与已接受的边界

- **更换 Key 后手动探测新额度，满足日常使用。** 额度快照来自个人提交 `eedc8c1f8`，`f2973866e` 后用于调度；本轮清理之前已存在持久化快照按账号 ID 保存的边界。本轮已隔离不同凭证的内存缓存。**个人版处理方式：** 保存新 Key 后，点击额度窗口中的刷新/探测按钮并确认成功，会读取新 Key 的额度并写回快照。后台调度也会在额度快照缺失或超过 30 秒有效期时按需刷新；没有独立的上游额度定时扫描。账号页面的 30 秒轮询只读取已保存数据，列表顶部刷新也不等于上游额度探测。旧探测恰好在换 Key 后迟到写回的竞争作为低频边界接受，不为此增加条件写入和跨层身份协议。位置：`backend/internal/service/upstream_userinfo_quota_service.go:201`、`:762`；`frontend/src/views/admin/AccountsView.vue:1630`。
- **同周期预算去重符合当前上游约定，不列为当前缺陷。** 个人提交 `dcff21688` 增加 `/user/info` 补读，并在 `userInfoMergeUserWindow` 中按周期去重。本轮未改变其合并规则。用户已确认当前上游的 Key 预算和用户预算相同，保留一份可避免重复展示，沿用现实现。此前提出的“两层独立同周期预算”是当前约定之外的配置，撤回针对本项目的优先整改建议。以后上游实际改成独立预算时，再做针对性补丁，不提前增加通用 `scope` 模型或改造前后端协议。位置：`backend/internal/service/upstream_userinfo_quota_service.go:1015`。

- Redis 容量脚本统一通过 `reply` 刷新 TTL，删除重复执行的四组 `EXISTS`/`PEXPIRE`，以及已被前面分支返回覆盖的结果分支。

## 可选优化（出现实际需求时再做）

1. **等待耗时明显超出配置时，修正计时起点。** `ustc_pool_coordinator.go` 当前在任务第一次选号失败之后才设置 deadline；排在慢任务后的首次派发耗时未计入 `fallback_wait_timeout`，而 Redis 许可从进入队列前就开始计时。届时可优先改为入队绝对期限，不必预先给每一层调用增加预算机制；注意不能把调度阶段的短期 context 带入已获得的转发票据，否则选号返回即取消会使后续提交失败。
2. **观察到 Redis 元数据持续增长时，再回收崩溃遗留标记。** `ustc_capacity_cache.go` 清理过期租约时为迟到回包保留 `c:`、`cs:` 等标记；若进程崩溃而不再释放，持续使用的 Key 会不断续期整个 hash。个人低负载下暂不另建回收机制；确有增长时再清理已结束 epoch 的遗留票据，并保留必要的乱序保护。
3. **容量读取影响维护或页面速度时，再抽取共用逻辑。** 账号列表与分组容量各有一套按 Key 去重和限制选择逻辑，分组读取仍逐个访问 Redis。少量账号可以维持现状；后续确有重复修改或性能问题时，再考虑共享读取函数与有界并行。
4. **继续扩展调度条件时，再整理长参数列表。** transport 修复表明请求约束需要完整传递。后续增加条件时可复用已有 `OpenAIAccountScheduleRequest` 或提取小型结构；当前无需为统一形式同时改动整个上游调度器。
5. **按实际部署验证。** 现有原子状态机测试主要使用 miniredis，日常单实例部署做本地回归和上线后的基本观察即可。以后实际运行双实例，或出现断连、重启后的异常时，再补真实 Redis 的相应场景测试。已有单 Key 上游实测不能证明真实三 Key 池的总吞吐，也不能覆盖持续外部调用同一 Key 的情况，这些作为验证范围说明保留。
