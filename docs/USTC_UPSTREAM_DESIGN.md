# USTC 上游限流实测与调度设计

日期：2026-10-02，时区 Asia/Shanghai。设计已在个人分支实施，当前运行规则见 [USTC_SCHEDULING.md](USTC_SCHEDULING.md)。本文保留实测依据、设计取舍和验收范围。

目标：自动获取 USTC 的限制，本地维护与上游规则一致的请求窗口，均衡使用账号池；容量耗尽时有界等待，发现窗口错位时按上游提示保守重新同步。TPS 与金额额度窗口继续保留。新增行为仅适用于 api.llm.ustc.edu.cn 的 OpenAI API Key。

## 实测结论

使用环境变量提供的一把 Key 测试 deepseek-flash 和 qwen-chat。三轮共 64 个 HTTP 请求：59 个模型调用、5 个只读元数据请求。短请求最多输出 16 tokens，一次流式生命周期测试最多输出 256 tokens。未修改上游账号设置。

脱敏记录：[ustc-upstream-probe-2026-10-02.json](ustc-upstream-probe-2026-10-02.json)。

| 项目 | 实测结果 | 对设计的要求 |
| --- | --- | --- |
| 上限 | /key/info 返回 rpm_limit=20、max_parallel_requests=20，本次 tpm_limit=null | RPM 和并发上限可自动获取 |
| 普通响应 | 非流式成功响应包含 Key 级上限及剩余 RPM/并发 | 用作校准反馈，不能直接覆盖共享余额 |
| 流式响应 | 两模型的流式 200 均没有上述剩余额度头 | 本地记账必须独立工作 |
| RPM 范围 | deepseek-flash 用完后，qwen-chat 同样被拒绝 | 本次两模型共用 Key 级窗口 |
| 自然分钟 | 跨过 :00 后仍被拒绝 | 不能按自然分钟清零 |
| 窗口边界 | 首次请求后 58.501 秒仍为 429；60.251 秒发出的请求成功，剩余 19 | 与首请求锚定的约 60 秒固定窗口一致 |
| 整体重置 | 首请求后约 62 秒连续成功，剩余 19、18；另外 19 个旧请求才过去约 54 秒 | 本次不是逐个请求在最近 60 秒中到期的严格滚动窗口 |
| 重复拒绝 | 旧窗口第 55 秒再次 429，第 62 秒已恢复 | 拒绝不把真实窗口延长 60 秒 |
| 恢复提示 | RPM 429 的 Retry-After=60，reset_at 随拒绝时间后移 | 提示是保守重试时间，不是窗口真实起点 |
| 并发 | 长流运行时另一个请求剩余并发 18；流结束后新请求剩余并发 19，RPM 继续递减 | 并发与 RPM 分别维护，流结束即释放并发 |
| 元数据 | RPM 耗尽时 /key/info、/user/info、/v1/models 仍为 200 | 元数据端口成功不能证明模型调用已恢复 |
| 失败计数 | key_model_access_denied 403 未消耗 RPM；空 messages 的 400 消耗了 RPM | 不能对所有失败调用退款 |

边界测试将客户端恢复区间缩小到约 58.6～60.7 秒，未直接取得服务端窗口起始时间。响应报告 LiteLLM 1.102.1；同版本源码的首请求窗口、前置 RPM 记账、活动并发槽及 now + window_size 恢复提示与观察吻合。版本号不能证明 USTC 没有自己的补丁。

只有一把 Key 可用于实测，未测另外两个账号的独立总容量。未主动触发金额预算耗尽、TPM 限流或 20 个长期流跨窗占槽；这些不能作为已验证结论。

## 自动限制与保留的 UI

复用现有 /key/info 后台刷新，增加 rpm_limit、max_parallel_requests、tpm_limit 的解析、缓存和更新时间；继续使用 /user/info 合并用户级金额窗口。本次 Key 级 RPM/并发来自 /key/info 的 info，不依赖其他 Key 的配置。

USTC 无需手填账号 RPM、并发，也无需配置粘性缓冲和三态 RPM 策略。并发完全使用自动获取的上限；旧的手填值不再约束 USTC，避免默认值过低浪费上游能力。

账号页仍显示：

- 自动获取的 RPM、并发上限及更新时间。
- 窗口已用/可用次数、当前活动并发。
- 正常窗口预计恢复时间，或上游给出的保守重试期限。
- 等待 RPM、等待并发、重新同步、额度耗尽等实际阻塞原因。
- 原有 TPS 和 3h/12h/24h 金额额度窗口。

尚未获取到的限制显示未知，不显示为 0 或无限。探测暂时失败保留最后一次有效配置；全新账号先读取配置，不能让高并发无约束地通过。缺失、null 和数值零不能混用，零值语义按上游协议处理。

budget_reset_at 是金额预算重置，不是 RPM 重置。60 秒是本轮确认的 USTC RPM 参数，不是从金额窗口推导的。

## 本地镜像与原子预占

计数范围是上游 Key，而非分组。重复导入、一个账号进入多个分组、多个后端实例不能各获得一份 20 RPM。运行状态使用不泄露凭证的 Key 指纹；更换 Key 更换状态。Redis 保存共享状态并使用服务端时间，重启继承尚有效的窗口。

最小状态包括窗口代次、首个实际转发时间估计、已占用次数、待提交预占、已知上限及同步状态。配置和额度快照可以落库；高频计数不随每次请求写数据库。

准入顺序：

1. 从可用候选中选号，立即取得并发槽；没有槽就等待整个池。
2. 最终转发前原子预占 RPM；没有额度就立即释放槽，等待时不占槽。
3. 第一单实际转发建立窗口；入队和提前选号不能启动窗口。
4. 发出后保留 RPM，响应体结束或确定断开时释放并发。

等待不占并发或 RPM。发送前取消退还预占；每份预占携带窗口代次，旧窗口退款不能扣减新窗口，跨界尚未发送的预占在提交时重新验证。窗口到期后由下一次实际转发启动新窗口，空闲时不创建周期性空窗口。

长流跨过 RPM 边界仍占并发，不能跟随 RPM 清零。一般发送后的 400/5xx/网络不确定错误保守计入 RPM；已验证的准入前权限拒绝可以单独退款，不对所有失败广泛退款。

## 错位时保守重新同步

采用用户确定的保守方案：正常状态镜像窗口，发现不一致后暂停该 Key 的新发送，按照上游提示等待，不用频繁提前试探追逐恢复边界。

状态可以收敛为：

    READY -> 观察到窗口不一致/RPM 429 -> SYNC_WAIT
    SYNC_WAIT -> 保守期限到达且存在请求 -> VERIFY_ONE
    VERIFY_ONE -> 成功并确认新窗口 -> READY
    VERIFY_ONE -> 仍为 429 -> 更新上游提示 -> SYNC_WAIT

具体规则：

1. 429 后设置共享 not_before，停止该 Key 后续新发送；未提交预占取消或在提交时否决。已发出的请求保守记账，并发按真实生命周期释放。
2. Retry-After 为秒数时，从收到响应的时间开始等待。reset_at 与 Date 都有效时，以服务端相对时差换算本地等待，减少两端时钟偏差；有多个有效提示取较晚者。
3. 没有可用提示且已识别为 Key 级 RPM 错位时，以已验证的完整 60 秒窗口保守等待，避免原来的通用 3 秒冷却。
4. 到期不是预先创建新窗口，而是只放行一个真实排队请求。新窗口以这次实际发送的时间建立；空闲十秒后才有请求，就从十秒后的实际发送开始计时。
5. 非流式反馈若显示剩余上限减一，可确认新窗口；若只有部分余量，先使用确认的余量，并以本次观测后完整 60 秒作为旧窗口结束的保守上界，不伪造精确起点。
6. 仍为 429 就重新按提示等待，不让等待者一起试探。纯流式成功没有剩余头，不能据此证明获得了整份 20；重新同步仍需满足无外部调用且旧窗口已完整过去的前提，必要时做一次极短非流式校准。

首次导入或 Redis 状态丢失时，优先使用一单真实非流式请求校准。首次为可重放的 Chat Completions 流式需求时，实施一次同模型、max_tokens=1 的非流式校准；它消耗 1 RPM，必须计入窗口，不是零开销。无法校准的入口保守等待完整窗口。取得部分旧窗口余量时按上述保守上界处理。成熟窗口和已知冷却后的恢复验证不额外发健康探测。

返回时间只是重新尝试期限，不能直接固定为以后所有本地窗口的边界。重新同步可能牺牲一次窗口的部分等待时间，这是明确接受的稳健性取舍；稳态仍按真实硬上限使用容量。

外部客户端持续共享同一 Key 时，当前端口没有完整计数/窗口起点，无法保证绝对镜像。全部调用经过本项目且共享 Redis 时，保守期限后的第一单可以重新建立一致窗口；外部仍在用则以反馈收紧余量并重新同步。

首请求在服务器的实际准入瞬间仍有网络误差。实现记录发送到首部确认的时间范围，并选保守边界或明确的小裕度；不要假定本地发送时间就是服务端精确窗口起点。非流式首部可能较晚，不能把响应体结束当作所有请求的窗口起点。这是剩余的时间精度取舍，不是多增加一套限流策略。

## 响应校准与其他限制

普通响应中的余量来自准入时快照，返回可能乱序。反馈必须携带请求窗口代次并结合尚未被快照覆盖的本地预占处理；不能把迟到的 remaining=19 赋给已有多个在途请求的账号。无法确定覆盖关系时只收紧估计或重新同步，不因旧回包增加额度。缺少响应头不代表无限。

并发不足等待槽释放；RPM 用尽等待窗口；金额预算耗尽按现有预算快照和 reset 判断。权限错误不把整号误记为 RPM 冷却。未识别的 429 类型遵守重试提示并记录原因，不能套用已验证的 requests 窗口。

多个金额窗口/冷却条件必须全部解除才能准入；整个池关注最早真正可用的账号，而非只取某个较近的 reset。

## 均衡分配与池等待

同模型兼容、同显式优先级的可用账号，按已占用次数/上游 RPM 上限选择最少者，同值轮询；预占立即参与排序。三号同为 20 时，同一波请求中的分配差应不超过 1。普通会话不再享有超额粘性缓冲；确有 previous_response_id 上游状态绑定时保留绑定，仍受硬上限约束。

窗口相位或健康状态不同，短时集中到先恢复的账号可能合理。已有容量不能为了等其他号恢复而闲置；平均是对当时可用候选的分配，不是强制所有账号同步恢复。

每个进程的每个池保留一个等待协调器，管理有界队列和最近恢复定时器。新请求不能持续抢在已可调度的等待者前面；绑定到不可用账号的请求不阻塞能够使用其他号的请求。槽释放、未发送预占退款、窗口到期和配置变化触发重新派发。

复用现有等待时长、等待人数和跨实例等待许可，不新增分布式队列选主。跨实例准入原子共享，进程内提供顺序公平；严格全局 FIFO 不属于本次目标。需要兜底检查时按池合并一次，不让每个等待请求每 200ms 独立重跑数据库、选号和探测。

若全部候选已提交用完 RPM，最早已知恢复超过请求等待期限，就及时返回 429 与 Retry-After。并发忙或有可退款的未发送预占时，不能仅凭 RPM 表象断言等待无意义。缓存不可用不能让每个实例自行获得一份无限预算，应返回可重试的基础设施错误。

三把健康且独立的 20 RPM Key 稳态容量约 60 次/分钟。队列吸收短暂突发，长期输入高于容量必须返回可重试的过载响应。发现错位后的保守等待可能降低那个周期的吞吐，但避免反复超发。

## 落地范围

已连续完成三个步骤：

1. 元数据自动限制和 USTC 窗口预占；去掉 USTC 三态/缓冲，使通用自然分钟 RPM 不再负责 USTC。
2. 在共同转发生命周期接收反馈并分类 429；HTTP、流式、转换入口和续链共用 Key 状态，不受 OpenAI 实验选号开关影响。
3. 保留候选资格与额度后台刷新，池协调器替换每请求轮询；UI 保留并调整 RPM、并发和恢复时间显示。

主要落点是 upstream_userinfo_quota_service.go、ustc_capacity_cache.go、ustc_admission.go、ustc_account_scheduler.go、ustc_pool_coordinator.go、ratelimit_service_ustc.go、共同转发入口及账号编辑/展示页面。上限变化不能重置已使用计数；降低上限立即收紧，当前窗口内提高上限不放大已确认容量。

保留原有 Anthropic RPM 行为；撤销个人分支把账号 RPM 扩展到所有 OpenAI API Key 的范围。混合分组中仅 USTC 成员使用新规则。TPS 与金额额度窗口不依赖这套运行计数。

## 验收标准

- 三号 60 次突发公平、不超额；自然分钟跨界不提前重置。
- 正常窗口到期及时派发；错位遵循保守提示；到期只有一单验证；空闲后首单才建立窗口。
- 旧回包、旧退款、跨窗未发送预占不污染新窗口。
- 重启、多分组、多实例和重复 Key 不产生额外额度。
- 长流跨窗仍占并发；400 与已验证的准入前 403 正确记账。
- 元数据缺失不变为无限；队列满、超时、取消释放全部等待资源。
- UI 仍展示 RPM/并发上限、使用量和恢复状态，自动读取失败显示未知或上一次结果。
- 非 USTC 调度、原有 Anthropic RPM、TPS 和金额额度窗口回归。
