# USTC 速度观测：展示设计、任务规格与实测

状态：已接入正式应用，入口为管理后台「速度观测」(`/admin/ustc-speed`)。真实调用由现有使用记录同步，定时基准共用此入口；基准任务默认停用，开启前可配置账号、模型、频率、Cron、参数和保护。

当前实现包括 TPS / TTFT / 各阶段耗时趋势、来源与模型/账号/请求条件筛选、原始点和时间分桶 P10/P50/P90/平均值、单真实系列桶级 P10–P90 分布带、按本地小时的调用时段分布、样本下钻及 CSV/JSON 导出。真实调用不新增模型请求，也不在网关被动采集：速度直接由使用记录中的总耗时、首字时间和 token 数计算，因此没有事件级阶段耗时、输出停顿和可靠的结果状态；这些字段只对定时基准样本采集。基准时长从请求发往上游计算，不包含 Sub2API 本地等待。下文第 2 节保留完整分析设计蓝图，自动发现、相关性热图、到达过程曲线等扩展视图尚未接入。

基准走现有 USTC 共享准入，预留 RPM 和并发、用户排队时让位、按物理 Key 限制后台请求；冷启动校准同样计入共享 RPM 和并发。连续 429 会缓测或暂停，当前探测视图可明确标记最近有效真实调用替代。任务修改使用版本与租约保护，旧执行不会覆盖新调度。速度观测长期保留，不自动过期删除，使用记录持续同步覆盖真实调用；每日请求和 token 预算已移除。

本地交互式原型位于 `docs/ustc-speed-dashboard/index.html`（未纳入版本库与镜像）。它使用本轮十条真实样本，以全宽 TPS、TTFT、各阶段 Time 趋势图为主体；其它分析默认折叠。支持时间范围、指标和模型切换，以及请求详情。原型配置只供预览，不会发起测试；正式功能由应用页面提供。

## 1. 页面首先要回答的问题

- 现在选哪个模型、哪个账号？首字快、持续生成快和稳定，可能是不同选择。
- 今天哪个时段适合长任务？某个时段是偶然快，还是多天都快？
- 多个账号是否同时变慢？是否只有个别账号持续偏离其他账号？
- 一次请求为什么感觉慢？本地等待、上游开始输出、思考到正文、正文生成和中途停顿各用了多久？
- 429 或忙时暂停基准以后，目前还能从真实调用中观察到什么？哪些时间段没有可靠数据？

默认界面围绕这些问题组织；高级筛选和配置放在展开面板，避免首页堆满指标。

首页可生成可点开的简短发现，例如“当前变慢主要出现在首次正文等待”“这一轮多数账号同步下降”“某账号多轮持续低于同轮均值”。每条发现显示比较范围、样本量、覆盖与数据来源，点击直接筛选到证据；证据不足时不生成判断。

不建议用一个不透明的“综合评分”决定优劣。默认并列展示速度、等待、稳定性与成功率；允许用户按自己的阈值定义“体感达标率”。

### 页面组织与分析选项

只保留一个主导航入口 **速度观测**，默认收起。展开后切换图表分析或检测配置；真实调用统一在已有“使用记录”页查看，不把每种分析各做一个平铺标签页。

页面主次固定：主体是全宽 TPS、TTFT、各阶段 *-time 趋势图，三类图通过同一选择器切换；关键数字只是图下方的紧凑辅助信息，不占用图表的主要空间。模型对比、输出过程、发现和调用明细全部收纳进默认折叠的辅助分析区，不与主图并排争夺注意力。真实/基准、模型和日期作为筛选，不再增加一排标签页。

横轴固定为服务端实际应用的完整起止范围；单点或稀疏数据也不自动伸缩到多年跨度。页面显示已应用日期，所选范围内没有调用的时段留空。真实调用的时间桶均值使用柱状图，原始调用使用散点；基准的聚合结果使用趋势线。只显示一个真实系列时，柱后叠加该时间桶的 P10–P90 分布区间，悬浮提示同时给出 n、P10/P50/P90 与低样本提示；多系列时避免区间带相互遮挡，分布仍保留在提示中。

主图下方固定展示“调用时段分布”：按页面所选时区把已应用范围内的有效调用聚合到 0–23 时，每个模型/来源一条线。它回答“什么时候调用更快”，与时间桶趋势互补；没有有效调用的小时留空，不补零。时段统计使用与服务端相同的模型、账号、日期和条件筛选，分布与均值都来自调用级原始观测。图例默认只显示模型名；仅当同一模型同时存在真实与基准数据、需要区分两条线时才附加来源。

时间范围沿用使用记录页的 DateRangePicker（frontend/src/components/common/DateRangePicker.vue）：今天、昨天、最近24小时、最近7天/14天/30天、本月、上月，以及开始/结束日期和“应用”。正式页面直接复用现有组件；本地静态预览对齐相同操作。“最近24小时”提交为以当前时刻为终点的精确滚动窗口（`last_hours=24`），不用“昨天+今天”两个整日近似；其它预设按所选时区的整日范围查询。更改时间范围联动曲线、计数、记录和导出；无样本时显示空状态，不填零。页面主“应用”按钮也会提交日期选择器中尚未应用的日期，避免选择被丢弃后跳回旧范围。

检测任务列表放在配置页最前方，每个任务直接显示“每 N 分钟/小时”并提供修改入口；编辑对话框中间隔使用秒/分钟/小时输入，提交仍为秒数。全局采集与后台并发设置收纳在折叠区。启用任务（或新建即启用）会尽快开始首轮，而不是等待完整间隔；列表每 10 秒静默刷新状态。最近一次运行的跳过原因写入任务并在状态下方显示，同轮日志同时记录各账号的跳过原因，便于检查用户负载、容量预留、共享准入、429 缓测或起跑差限制。

TPS 可切换生成速度（不含首字等待，输出阶段 token/秒）与平均速度（含首字等待，输出 token/整个上游请求耗时）；TTFT 可切正文首字与首次有效输出；Time 优先展示最大输出停顿与输出后等待，也可选响应头和输出阶段。时段分布图使用与主图相同的指标口径。任务总耗时只保留在单次记录详情，不作为主图趋势指标。生产路径以后若采集到本地等待等时间再加入选项，不能把响应头时间冒充模型 prefill/排队时间。

账号对比、时段规律和输入/缓存实验在有数据、确实需要时收纳进辅助分析选择器。首页始终以速度和耗时图为主，不把所有图表同时堆出。检测配置优先使用弹层或抽屉。

点击任何点或热图格子可下钻到轮次/请求抽屉，展示阶段瀑布、到达曲线、计数、结束原因与原始指标。保留筛选条件、导出 CSV/JSON，并支持保存分析视图。

常用筛选为模型、账号、真实/基准/对照、时间范围。高级选项包括配置版本、思考模式、输入/输出长度、缓存、协议、状态、时区、聚合粒度、分位数、对照日期和固定账号集合。允许切换图表指标，但提供能直接使用的默认组合。

## 3. 账号并行测试与“平均值”的口径

每个检测轮次固定一个模型和测试配置，对选中的不同物理 Key 尽量同时发起请求。提示集合的选择与调度抖动在轮次层统一决定，不能各账号随机换题后宣称是同条件比较。模型权限不足的账号标为不适用。

每轮保存 round_id、计划时间、实际启动时间差、应测/已测/有效/跳过/失败的账号集合和原因。模型轮次之间错峰，同一 Key 默认最多一个后台测试。全局上限或用户负载导致无法同时开始时，超过允许起跑差的样本标为未对齐，不悄悄把串行结果纳入严格同轮对比。

所有来源采用相同口径：先按模型、账号和日期筛选，再将各时间桶内的有效调用等权平均。每次有效调用权重相同，不额外计算账号均值后再平均。选择一个账号就统计它的调用，选择多个账号就合并所选账号的调用；基准任务每轮按物理 Key 去重发起。失败或跳过不记作 0 TPS，也不能从失败率和覆盖中消失。账号长期比较使用固定账号集合或明确标出集合变化，避免慢账号缺席后平均值虚高。

真实工作与基准都按筛选后的调用平均，不提供额外的账号视图或账号等权开关。账号并行的“总吞吐”是另外一个指标，不能把单请求 TPS 的平均或相加直接当作平台总吞吐。

多账号同步变慢可以提示共同影响；账号间相关性不能单独定位 GPU、内部路由、Key 优先级或网络原因。USTC 的缓存与调度确实会变化，可将已知维护作为时间轴注释，见 [USTC 技术更新](https://llm.ustc.edu.cn/guide/technical-updates/)。

## 4. 采样与连续 429：保障用户优先

真实调用由使用记录持续同步，固定基准提供空闲时段的数据。两种来源独立统计、并列展示。建议初始基准为每模型、每物理 Key 30 分钟一次，轮次约 ±3 分钟抖动；间隔可配置，不把本轮几分钟的实测当作最优频率的依据。

按非思考配置每次 512 输出 token 估算，每模型、每 Key 每日 48 个基准任务，最多 24576 输出 token；总成本还需乘模型数和物理 Key 数，并加上输入、校准、思考、重试和复测。运行频率直接在任务中设置；不另设每日请求或 token 预算，仍服从账号的共享容量与上游额度。

探测必须走 [现有 USTC 共享准入](USTC_SCHEDULING.md)，计入真实 RPM、并发和额度，不通过独立 curl 绕开容量状态。没有用户排队、保留足够 RPM/并发余量、账号不在额度阻塞状态时，才允许启动低优先级后台请求。已预占但未发送时用户任务到来应让位；已经发出的请求无法退还已消耗的 RPM。

429 策略按物理 Key 共享，并区分类型：

- 本地容量不足：跳过并显示“用户繁忙/容量不足”，不标成上游性能故障。
- 上游 RPM/并发 429：遵守共享冷却及 Retry-After；真实调用和探测中的真实上游反馈都可提供压力证据。
- 金额预算 429：等预算窗口恢复，期间继续获取允许的额度元数据，不继续发生成请求试探。

可配置的起始策略是：15 分钟内连续 3 次真实上游 429，后续基准间隔翻倍，最高 2 小时；持续出现则暂停自动基准。跳过本身不增加失败连续次数，成功上游请求可打断连续失败。恢复需要满足现有准入和预设成功/低负载条件，不用单独的频繁重试抢跑冷却。无人使用且冷却结束时，若共享准入允许、没有用户排队，可以只放行一单低优先级半开验证；多人和多实例不能一起试探。

暂停/缓测时，当前状态自动展示最近真实调用，带“基准暂停，使用真实数据”、任务条件和数据年龄。只有条件足够相近时才提供对照；真实任务不能伪装成固定基准或填进缺失的同轮账号测试。无新真实数据就显示过期/无数据。

异常复测与定时基准分开标记。可在非限流、容量充足时，间隔 3–5 分钟补最多 2–3 次确认；额外样本不混入固定基准的时段统计，避免“慢时测得更多”扭曲时间规律。

过去没有采集的时段无法事后补回，缺失不填 0、不通过插值伪装完整。30 分钟探测不能保证发现几分钟故障，因此展示“探测成功率”与覆盖，而不是声称精确的时间可用率。

## 5. 检测任务配置清单

配置完整，但默认只暴露必要项，其他放在高级设置。以下均应具有清晰默认值、能力校验与配置版本。

| 配置组 | 应支持的选项 |
| --- | --- |
| 基本信息 | 名称、说明、标签、启停、负责人/创建者、配置版本 |
| 测试目标 | USTC 账号多选/全部、物理 Key 去重、模型多选、权限不足的处理、固定或自动更新的账号集合 |
| 测试配置 | 短/中/长输入预设、自定义合成提示和提示集合、语言、同轮统一选题、实际输入长度记录 |
| 协议与流式 | 模型支持的 Chat Completions/Responses 等入口、流式/非流式；不支持某项能力时明确不可用 |
| 生成参数 | 输出上限、temperature、top_p、seed/stop 等模型支持项；扩展请求参数需保存实际生效值 |
| 思考 | 关闭/开启、reasoning effort/预算、模型参数映射、预期是否需要正文；不静默忽略不支持参数 |
| 缓存实验 | 固定前缀/不同前缀配置、缓存命中记录、分开比较；上游不支持禁缓存时不宣称强制冷缓存 |

| 负载保护 | 用户队列门槛、RPM/并发预留、活动请求阈值、额度余量、最长占用时间 |
| 429 与恢复 | 连续次数和观察窗口、缓测倍率、最大间隔、暂停条件、成功/低负载恢复条件、共享冷却优先 |
| 真实数据替代 | 启用条件、最大数据年龄、最低样本数、可比条件、来源标记、无数据状态 |
| 异常判定 | 首字/正文等待、TPS 下降、长间隔、超时/错误阈值；相对历史基线和绝对阈值可分别设定 |
| 请求边界 | 连接/首个输出/整体超时、取消、输出上限结束、失败/重试规则；基准不自动回退到别的模型/上游 |
| 数据与展示 | 聚合粒度、低样本显示门槛、默认对比时段/指标、导出与保存分析视图 |

思考或非流式配置没有某些指标时，应显示不适用。全面的选项不意味着每个模型都支持所有参数；启动前验证，并保存实际发送和实际观测到的配置。

## 6. 数据采集、统计与保留

真实调用不在网关被动采集，也不保存提示或回答正文：后台从 `usage_logs` 同步最近 24 小时的记录，按 `legacy_usage_id` 去重，每 5 分钟刷新一次；首次启用或升级后从功能起始时间向上补齐，追平后改用 24 小时滚动窗口。速度由记录中的总耗时、首字时间和 token 数计算。基准任务使用受控的合成提示，并在请求生命周期中采集事件级首字、输出停顿、结束原因和思考/正文拆分。

| 数据组 | 主要内容 |
| --- | --- |
| 轮次与来源 | 任务/配置版本/round_id、开始时间、真实/定时/复测/手动、采集位置、账号及内部物理 Key 身份、调度状态与原因 |
| 请求条件 | 请求/实际上游/响应声明模型、思考参数、服务档位、入口和上游协议、输入/输出长度、缓存状态 |
| 用量与结束 | 输入、输出、reasoning、cached token、计数来源、上游消耗、实际结束原因、是否只产生思考 |
| 阶段耗时 | 本地等待、实际上游发送、响应头、首次有效输出、首次正文、末次有效输出、完整结束 |
| 流畅性 | 思考/正文/工具输出分类，有效事件数、最大无输出间隔、超过阈值次数与时长；排除心跳/空事件/role |
| 失败信息 | HTTP/流式错误、限流范围、超时、中断、用户取消、逐次尝试与最终请求结果 |

持续时间和调度间隔使用单调时钟，UTC 时间用于定位和对齐；时钟校正不能产生负耗时或错误的请求重叠判断。正式数据以 NAS 的实际转发路径为准，WSL 实测、NAS 和浏览器网络观测分开标注，不直接合并。

首次有效输出可能是思考、正文或工具参数。正文速度不能拿包含思考的 token 数除以正文阶段耗时；没有可拆分的计数就只展示可观察指标。SSE chunk 不等于 token，只有终态总用量时不伪造精确的逐秒 TPS，可用累计字符/字节和长间隔展示到达过程。

基准的生成速度使用首次到末次有效输出；真实调用只能使用使用记录的 output/(总耗时−首字) 近似，首块 token 数未知时明确标近似。总速使用完整请求耗时。两种口径在对照时注明来源，不能把近似公式当作精确事件计时。定义参考 [NVIDIA 的指标说明](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/perf_analyzer/genai-perf/README.html#metrics)。

默认对通过模型、账号、时间筛选的调用，按模型、来源和时间桶直接求原始有效观测的平均值；不将输入长度、缓存、思考等条件拆成大量曲线，这些条件用于高级筛选或单次详情。时段分布同样直接在原始有效观测上按用户时区的小时聚合，不对已汇总的分位数再求平均。自动时间粒度为 48 小时内 1 分钟、8 天内 5 分钟、31 天内 15 分钟、更长时间 1 小时，也可手动选择。需要分布分析时可切 P10/P50/P90，直接从原始观测计算，不平均已汇总分位数。

统计展示都携带 n、有效覆盖、来源、最新时间和不可比较原因。可先约定不足 5 个样本以原始点为主、5–19 个只展示中位数与低样本提示、达到 20 个再显示分布区间；这些是展示门槛，不是置信保证。失败、取消、输出上限截断、仅思考和忙时跳过分别统计，不能只留下成功且快速的样本。

明细与速度指标长期保留，不按天数自动删除。跨窗口分位数用原始样本、可合并直方图或分位数摘要计算，不能平均各窗口 P50/P90。定时探测、异常补测、请求加权与时间覆盖各有口径。

## 7. 2026-10-25 实测结果与展示启发

凭证来自用户授权的 Windows 系统环境变量 USTC_LLM，仅在进程内读取，未保存。脱敏摘要和截图保留为本地 `docs/ustc-speed-probe-2026-10-25.json`、同名 `.png`，不纳入版本库或镜像。

本轮 2 次元数据请求、10 次串行模型调用，并发 1、按单调时钟 10 秒最小启动间隔调度。10 次均为 HTTP 200，正常收到结束标记，合计 2475 输入 token、4160 输出 token（其中 512 为 reasoning）。usage.cost 合计 0.0114，API 未声明货币单位，不推断汇率。/key/info 返回 RPM 20、并发 20、TPM null。

| 配置 | 近似生成速度 | 首次正文 | 展示启发 |
| --- | --- | --- | --- |
| Qwen chat，512 输出，3 次 | 34.6 / 63.3 / 31.8 TPS | 1.03 / 0.83 / 3.55 秒 | 同条件也会波动，应保留散点、分布和样本量 |
| DeepSeek，关闭思考，512 输出，3 次 | 25.0 / 29.8 / 29.1 TPS | 0.31 / 0.15 / 0.15 秒 | 首字快和生成快是不同维度 |
| DeepSeek，默认思考，512 输出，1 次 | 20.8 TPS，全部是思考 token | 没有正文，达到输出上限 | “首个输出 0.30 秒”不能标成“0.30 秒开始回答” |
| Qwen chat，32 输出，2 次 | 43.5 / 32.3 TPS；总速仅 14.4 / 10.5 TPS | 1.48 / 2.07 秒 | 短任务受等待占比影响大，不能和长输出总速直接混算 |
| DeepSeek，关闭思考，2003 输入，1 次 | 23.1 TPS | 0.45 秒 | 需要记录输入长度；仅一条数据不足以推断长上下文规律 |

最快的一次 Qwen 请求约 63.3 TPS，但中间出现约 1.94 秒没有新的有效内容到达；另一次约 31.8 TPS，最大间隔约 0.45 秒。这直接支持同时展示“平均速度”和“流畅性”，而不是只按 TPS 排名。

测试响应包含 reasoning_tokens、cached_tokens 和 cost。所有样本的 cached_tokens 均为 0，不能据此比较缓存效果。512 token 请求的有效 SSE 内容事件约 190–316 个，证明 chunk 与 token 不是一一对应。

本轮近似生成 TPS 使用 (completion_tokens−1)/(末次有效输出−首次有效输出)，假设首事件含一个 token，实际首块 token 数未知。默认思考样本独立展示，不与非思考正文混算。全部请求为受控速度测试并达到输出上限，不是任务完整回答或质量测试。

实测仅一把 Key，每种主要可比配置仅 3 次重复，不能得到账号并行、全天/星期规律或可靠尾部分位数的结论。Python urllib 为请求新建连接，包含 WSL 网络、环境代理和连接建立影响。公开响应模型仍是别名，无法确定内部部署。没有出现 429，退避策略尚未通过这轮实测验证。

## 8. 功能验收重点

1. 真实调用与定时基准都可分析，支持单账号、同轮平均和固定账号集合比较；每项指标来源和统计口径明确。
2. 账号基准按物理 Key 去重，同轮条件一致、起跑差可见，部分失败不会制造“平均变快”的假象。
3. 任务配置覆盖目标、输入、协议、思考、采样、并行、负载保护、429、恢复和数据替代。
4. 连续 429 能缓测/暂停并使用带来源标记的真实数据；恢复遵循共享准入，忙时保护与跳过原因可检查。
5. 总览能看当前状态，账号页能看共同/个别波动，规律页能看时段与任务条件，单样本能看阶段和卡顿。
6. 低样本、缺测、无正文、过期、取消、输出截断、参数不适用都有真实状态；不以伪精确分位数、填 0 或混用来源掩盖问题。
7. 页面展示探测成本和容量占用，并能检查用户等待时是否启动了后台基准。上线先验证真实请求的等待与失败分布，再决定频率是否需要调整。
